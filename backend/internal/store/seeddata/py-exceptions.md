## 第8章 · 异常处理

程序运行中总会出错：用户把年龄输成了"abc"、要读的文件不存在、列表下标越界。Python 遇到这类问题时会抛出异常（exception），如果没有人处理它，程序立刻终止并打印一长串错误信息。对学习来说这没问题，但交付给别人用的程序必须学会"接住"异常、妥善处理，这就是 try/except 的工作。

基本结构是：把可能出错的代码放进 try 块，用 except 捕获指定类型的异常。捕获时要写明异常类型，这是好习惯：

```python
try:
    n = int("abc")        # 这行会抛出 ValueError
    print("永远不会执行到")
except ValueError:
    print("请输入有效的数字")
except (TypeError, KeyError):
    # 一个 except 可以同时捕获多种异常，用元组括起来
    print("类型或键出了问题")
else:
    # try 里没有发生任何异常时才执行
    print("转换成功：", n)
finally:
    # 无论是否出错都会执行，常用来收尾，比如关闭资源
    print("处理结束")
```

except 后面写异常类型，就像医生对症下药：把 ValueError 写成裸的 except，所有异常都会被吞掉，程序表面正常、内里错误百出，是最常见的反模式。常见的异常类型先认识几个：

- ValueError：值类型对但内容不对，比如 int("abc")；
- TypeError：对不合适的类型做了操作，比如 "a" + 1；
- KeyError / IndexError：字典的键、列表的下标不存在；
- FileNotFoundError：文件不存在；
- ZeroDivisionError：除数为零。

有时不是代码写错了，而是使用方式不对——比如调用者传进来的参数本身非法。这时应该主动抛出异常，把问题明确地暴露出来，而不是默默返回一个错误的结果：

```python
def divide(a, b):
    if b == 0:
        # raise 主动抛出异常，附带说明信息
        raise ValueError("除数不能为 0")
    return a / b

try:
    print(divide(10, 0))
except ValueError as e:
    # as e 把异常对象接住，里面的信息可以打印或记日志
    print("捕获到错误：", e)
```

两条实践建议值得写进习惯里：

- 捕获的范围要小：只把真正可能出错的那一两行放进 try，而不是把整个函数包起来，否则真的错误会被掩盖；
- 处理不了的异常就让它继续飞：捕获后打个日志再 `raise` 抛回去，好过假装无事发生。

和第 5 章讲过的返回值 None 相比，异常的语义更强烈：None 可能是正常结果，而异常一定表示"出了问题"。写库函数时优先用异常报告错误，写日常脚本时优先把异常挡在用户面前。

异常类型也可以自己定义：写一个继承 Exception 的类，起一个见名知义的名字，比如 ContactNotFound，在 raise 处带上必要的上下文信息。项目有了自己的异常体系后，调用方可以精确区分"是业务规则不满足，还是底层出了故障"，分别决定提示用户还是记日志报警——这是从小脚本走向正式工程的标志性一步，在大一点的开源项目里你几乎总会遇到这样的异常类层次。

小结：try 探险、except 接住、else 庆祝、finally 收尾；raise 主动报告问题；except 必须写明类型，裸捕获是大忌。练习建议：改造第 5 章的通讯录，查询不存在的姓名时抛出自定义异常，在调用处捕获并友好提示。
